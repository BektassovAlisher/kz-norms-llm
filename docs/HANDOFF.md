# Контекст проекта (передача из облачной сессии)

## Цель
Проект в портфолио/резюме с упором на **fine-tuning**: локальная Qwen3-4B, дообученная через
QLoRA (Unsloth) на 8 ГБ GPU, отвечает на вопросы по строительным нормам РК **строго по найденным
пунктам**: JSON-ответ со ссылкой на пункт и дословной цитатой, либо `not_found`, если в нормах
ответа нет. Главный результат — таблица «base 4B vs fine-tuned 4B vs большая модель по API».

Целевой работодатель — казахстанский стартап **Armeta AI** (Armeta Gate — ИИ-проверка
проектно-сметной документации для РГП «Госэкспертиза»; Armeta MTO — спецификации из P&ID;
в вакансии AI Engineer: agentic LLM, tool calling, structured output, контроль стоимости/задержек,
IFC/DWG). Отсюда акценты: нормоконтроль, локальные модели (данные госзаказчика не уходят
наружу), строгий формат ответа, честные метрики.

## Архитектура (кратко)
```
sources.csv → ingest (parse docx/pdf → segment) → clauses.jsonl
  → index: BM25 (bm25s + pymorphy3) + BGE-M3 → Qdrant; реранкер bge-reranker-v2-m3
  → synth: учитель (большая open-weight модель по OpenAI-совместимому API) → filter → sft/
  → train: Unsloth QLoRA Qwen3-4B-Instruct-2507; дообучение BGE-M3 (sentence-transformers)
  → export GGUF → llama-server (JSON-схема) + FastAPI + Gradio (base и fine-tuned рядом)
  → eval: retrieval (Recall@5, MRR@10) и generation (oracle / end-to-end)
```
Запрос: вопрос → BM25 ∥ BGE-M3 → RRF → top-30 → реранкер → top-5 → промпт (тот же шаблон,
что в обучении, хранится только в `rag/prompts.py`) → LLM → Pydantic → `verify.py`
(clause_id из контекста, цитата — дословная подстрока пункта, числа из ответа есть в цитате).

## Ключевые решения
- **Сплит по документам** (train/val/test ≈ 70/10/20): синтетика только из train/val, ручной
  тест только из test-документов — меряем навык, а не заучивание. Индекс содержит все документы.
  Единица сплита — группа (`group` в sources.csv: СН+СП одной темы). **Дистракторы в
  контекстах SFT тоже только из train/val** — иначе test-пункты протекут в обучение.
- Тестовый набор: 150–200 вопросов, **проверенных руками**, ~25% без ответа в нормах.
- В SFT 20–30% примеров без gold-пункта в контексте → цель `not_found`; убедиться, что в
  контексте нет дубля gold-пункта (нормы повторяют друг друга).
- `verify.py` используется трижды: фильтр синтетики, рантайм, метрики.
- Оценка в двух режимах: oracle (gold + дистракторы — меряет LLM) и end-to-end.
- Сравнение base/ft только при одинаковой квантизации (обе Q4_K_M).
- Абляции: размер данных 500/1k/2k/4k (кривая обучения), доля отказов 0% vs 25%, r 8/16/32.
- Конфиги: `configs/*.yaml` (sft_qwen3_4b, emb_bge_m3, retrieval, synth).

## Источники норм
- С 2023 года строительные нормы как НПА отменены (приказ № 88-нқ от 26.05.2023), поэтому на
  adilet.zan.kz они «утратили силу» — **adilet не использовать** для текстов норм.
- Перечень действующих документов — **АГСК-1** (найденная редакция: приказ № 97-НҚ от
  20.06.2025 или новее). Тексты — ЕГФНТД: https://new-shop.ksm.kz/egfntd/ntdgo/kds/
  (запасной неофициальный вариант — smeta-kz.com).
- Издания двуязычные PDF: сначала казахская часть, потом русская.

Известные ограничения:
- Таблицы из PDF идут построчно без структуры; пункт В.10.2 пожарного СП ~10 тыс.
  символов — при индексации резать на чанки (можно попробовать `page.find_tables()` в PyMuPDF).
- В dostupnost-mgn подразделы начинаются с `.3` (так в самом документе), это не баг.
- Пропуск 5.5.30 был багом («…15 см. 5.5.30* Двери…» — звёздочка после номера), исправлен.
- В.5.16, В.6.\*, В.7.\* пожарного СП были проглочены ложным пунктом «В.8»: «…по Таблице» +
  новая строка «В.8 как для плит». Исправлено: после слова-ссылки (`REF_WORDS`) номер в начале
  строки — продолжение абзаца; кандидат в пункт с текстом со строчной буквы отбрасывается.
  Сейчас `kznorms stats`: разрывы нумерации только через пропускаемые «Нормативные ссылки»
  (и подразделы `.3` в МГН — так в документе), ни один пункт не начинается со строчной.
- Раздел 5.1 пожарного СП был нарезан со сдвигом на строку: в PDF номер пункта лежит на
  2–3 pt ниже первой строки своего текста и в потоке идёт после неё. Исправлено: `parse_pdf`
  собирает строки по геометрии (`visual_rows`: фрагменты, перекрывающиеся по высоте, — одна
  строка, внутри — слева направо). Побочный выигрыш: таблицы больше не теряют ячейки «I», «III»,
  «16» — раньше фильтр номеров страниц выкидывал их как отдельные строки (Д.8, Д.34, В.*).
  Цена: многострочные шапки таблиц перемешаны по строкам. Жилые нормы не изменились.
- Пометки «(Изм.ред. – Приказ … №57-НҚ)» остаются в тексте пунктов.
- `.vscode/settings.json` без пути к интерпретатору — VS Code сам находит `.venv`.

**Шаг 3 (готов):** поиск.
- `retrieval/chunking.py`: пункт → фрагменты ≤1200 символов с перекрытием 200 (по строкам и
  предложениям), к каждому спереди «doc_title. section». 722 пункта → 762 фрагмента
  (16 пунктов разрезано), ни один не длиннее 512 токенов BGE-M3. 1500 символов не влезало:
  таблицы с цифрами дают ≈2.5 символа на токен.
- `bm25.py`: bm25s + pymorphy3 (лемма, ё→е, числа «1,2»→«1.2», стоп-слова bm25s; «менее» и
  «более» оставлены). `dense.py`: BGE-M3 fp16 на CUDA, **Qdrant во встроенном режиме**
  (`artifacts/qdrant_local`, Docker на машине нет; для сервера — пустой `qdrant_path`).
- `hybrid.py`: RRF по пунктам (фрагменты сначала схлопываются в пункт по лучшему месту).
  `rerank.py`: bge-reranker-v2-m3 оценивает все фрагменты 30 кандидатов, пункт = максимум.
- `retriever.py`: `Retriever().retrieve(q, k, mode)` → `Hit(clause, score, chunk)`, режимы
  bm25 | dense | hybrid | hybrid_rerank, `timings_ms` по ступеням. CLI `index [--no-dense]`,
  `search "<вопрос>" [--mode] [--k] [--full]`.
- torch на Windows ставится из индекса PyTorch cu130 (`[tool.uv.sources]` в pyproject).
- Тайминги (3060 Ti, прогретый процесс): bm25 ~1 мс, dense ~20 мс, rerank 100–450 мс.
- На глаз: реранкер исправляет BM25 («ширина марша лестницы»: 5.3.9 с 3-го места на 1-е).
  Вопросы «высота потолка в квартире», «лифт в пятиэтажке» не находятся — **их нет в
  корпусе**: цифры лежат в своде правил СП РК 3.02-101 «Здания жилые многоквартирные», а у нас
  только СН РК 3.02-01-2023. Добавить его в первую очередь. Такие вопросы — готовые примеры
  `not_found` для тестового набора.

**Шаг 5 (начат): RAG на базовой Qwen3-4B.**
- `rag/prompts.py` (SYSTEM + `Passage` + `build_messages` — единственный шаблон),
  `rag/verify.py` (clause_id из контекста; цитата — подстрока текста, который видела модель,
  без учёта пробелов и ё; числа ответа — из цитат, номеров пунктов, кодов документов или
  самого вопроса), `rag/llm_client.py` (OpenAI-клиент, `response_format` json_schema,
  temperature 0), `rag/pipeline.py` (`RagPipeline.answer` → `AnswerResponse` c `problems`;
  ответ не по схеме → `not_found` + проблема). CLI `ask`. Тесты: `test_verify`,
  `test_pipeline` (подставные поиск и LLM).
- В Passage идёт лучший фрагмент пункта без заголовка «документ. раздел» (≤1200 символов),
  поэтому verify сверяет цитату с фрагментом, а не со всем пунктом.
- llama.cpp b12317 (CUDA 13.5, Windows) в `artifacts/llama/`, модель
  `artifacts/models/Qwen3-4B-Instruct-2507-Q4_K_M.gguf` (unsloth, 2,5 ГБ). Запуск:
  `artifacts/llama/llama-server.exe -m artifacts/models/Qwen3-4B-Instruct-2507-Q4_K_M.gguf
  -c 8192 -ngl 99 --port 8085 --jinja`. Видеопамять: сервер ~3,8 ГБ + поиск ~2,2 ГБ — влезает.
- Первый прогон (13 вопросов из теста, ручной разбор) — точка отсчёта для дообучения:
  - JSON по схеме — всегда (грамматика llama.cpp). LLM 1–10 с на вопрос.
  - **`status` не откалиброван**: идеальные ответы (q040, q048) помечены `partial`.
  - **Многословие и примешивание соседних пунктов**: q002, q010 добавляют лишнее из
    контекста; q005 сделала **неверный вывод** («душевые нельзя»), хотя процитировала пункт,
    где они разрешены — verify такое не ловит (цитата верная, вывод нет).
  - **Ложный отказ**: q020 (складной пандус) — gold в контексте, ответ `not_found`.
  - **Промах**: q050 — gold 5.5.31 в контексте, модель ответила по другому пункту.
  - Вопросы без ответа: q061, q063 — честный `not_found`; q058 — ответ по таблице
    одноквартирных домов (спорная разметка, пометка в `note`).
  - verify поймал пересказ вместо цитаты (q005, сауны) и число из вопроса (q067) — второе
    ложная тревога, исправлено (числа из вопроса разрешены).
  Всё это — ровно то, чему учит SFT: краткость, калибровка status, отказ только без опоры.

**eval-generation (готово): точка отсчёта базовой Qwen3-4B Q4_K_M.**
- `eval/eval_generation.py`, CLI `eval-generation [--drafts] [--modes oracle,e2e] [--limit N]
  [--reverify]` → `reports/generation_<model>.md` + `.jsonl` (все ответы с контекстом).
  - oracle: gold-пункты + трудные дистракторы (top поиска без gold), порядок перемешан с
    зерном = вопрос (воспроизводимо). Длинный gold — фрагмент, лучший по реранкеру.
  - e2e: контекст из поиска, как в проде. Вопросы без ответа — в обоих режимах top-k поиска.
  - метрики без судьи: answered, refusal_ok, verify_ok, gold_cited, numbers (числа эталона
    в ответе), status=answered при gold в контексте, длина, задержка.
  - `--reverify` пересчитывает verify и метрики по сохранённым ответам без LLM: генерация —
    минуты на GPU, проверка — миллисекунды.
- `pipeline.generate(question, passages)` отделён от поиска — oracle идёт через тот же код.
  Ответ, обрезанный по `max_tokens` (`finish_reason=length`), помечается отдельно.
- **Промпт v1 был с багом**: статусы `partial`/`not_found` описаны, `answered` — нет. Без
  схемы модель писала `"found"`, со схемой выбирала `partial` → status=answered 0/60.
  Ещё модель сокращала clause_id до «6.4.6». Промпт v2: все три статуса с определениями,
  clause_id «точно как в скобках», «отвечай кратко». Мораль: **сильный бейзлайн** — сначала
  выжать промпт, иначе дообучение «победит» баг промпта, а не базовую модель.
- verify v2 (после разбора реальных ответов): сравнение без учёта пунктуации, регистра, ё
  и пробелов («I -теплоизолирующей»); номера пунктов и коды документов из контекста — не
  «выдуманные числа»; маркеры списка «1)» — не числа; ошибки чисел разделены на «из
  контекста без цитаты» и «нет в контексте»; цитата из соседнего пункта называется явно.
- Результаты (67 вопросов test: 57 с ответом, 10 без; черновые, verify v2):

  | метрика | v1 oracle | v1 e2e | **v2 oracle** | **v2 e2e** |
  |---|---|---|---|---|
  | ответила (с ответом) | 0.96 | 0.98 | 1.00 | 1.00 |
  | честный not_found | 0.50 | 0.50 | 0.50 | 0.50 |
  | прошли verify | 0.87* | 0.84* | 0.77 | 0.89 |
  | процитирован gold | 0.85 | 0.84 | 0.86 | 0.84 |
  | числа эталона в ответе | 0.73 | 0.76 | 0.73 | 0.72 |
  | status=answered | 0.00 | 0.00 | 0.74 | 0.74 |
  | длина ответа, медиана | 223 | 263 | 164 | 201 |
  | LLM p50, с | 4.4 | 4.3 | 3.9 | 3.9 |

  \* v1 мерился старым verify, напрямую не сравнимо.
- Разбор:
  - **refusal_ok 0.50 — это разметка, а не модель**: все 5 «ответов на вопрос без ответа»
    — спорные вопросы с «РЕШИТЬ ПРИ ПРОВЕРКЕ» (q051, q055, q058, q062, q064 — в новом
    корпусе есть частичный ответ). На 4 бесспорных (q054, q059, q061, q063) — 4/4 not_found.
  - **Выдуманных чисел нет** (0 «нет в контексте»): все проблемы с числами — число из
    контекста, не покрытое цитатой (q010 «28 м», q049 «60 м», q023 «1,4–1,6 м»).
  - Ошибки цитат: модель «исправляет» опечатки нормы («зоной» → «зоне», «путь» → «пути»),
    пропускает слова внутри цитаты, приписывает цитату соседнему пункту (3 в oracle),
    один раз склеила clause_id (`sp-zhilye-zhilye-zdaniya`).
  - **oracle хуже e2e по verify (0.77 vs 0.89)**: контекст тот же (Hit@5 = 1.0), разница —
    порядок. В e2e gold обычно первый, в oracle перемешан. Похоже на позиционный перекос →
    в SFT gold ставить в случайную позицию. Выборка мала (≈7 вопросов разницы) — проверить
    на полном наборе.
  - e2e ≈ oracle по остальным метрикам, потому что набор лёгкий для поиска (gold всегда в
    top-5). Различать режимы начнут вопросы, написанные владельцем.
  - `numbers` шумная: «двух» ≠ «2», ссылки «табл. Б.1» в эталоне считаются числами.

**Шаг 6 (начат): синтетика — конвейер готов, ждёт API учителя.** `synth/` + CLI
`kznorms synth [--teacher big|base] [--n-clauses N]`, конфиг `configs/synth.yaml`.
- Этапы (каждый пишет файл в `data/synthetic/`): `select_chunks` (пункты только из
  train/val-документов, по случайному фрагменту на пункт; без таблиц и обрывков) →
  `gen_questions` (учитель: до 3 вопросов типов число / можно ли / условие / разговорный,
  «перефразируй, не называй пункт») → `build_contexts` → `gen_answers` (учитель отвечает
  по промпту прода `build_messages`, без подсказок о gold) → `filter` → `data/sft/
  {train,val}.jsonl` (messages = промпт прода + ответ учителя как assistant) + `report.json`.
- Контексты: поиск hybrid_rerank только по train/val-документам (test не протекает даже
  дистрактором); gold — в случайную позицию (позиционный перекос из eval); 25% примеров
  без gold → цель `not_found`.
- **Дубли gold в not_found-контексте** — главная ловушка. Сходство текстов не работает:
  sn-ovik:7.5.8 ↔ sp-ovik:7.5.8 (одно правило пересказом) — Jaccard 0.10, косинус BGE-M3
  0.73, а разные требования одной темы — косинус 0.88. Работает реранкер (вопрос+пункт):
  дистрактор < 0.6 × оценки gold — учитель всегда not_found, ≥ 0.9 × — почти всегда нашёл
  ответ. Правило: в not_found-контекст не берём пункты с оценкой ≥ `nf_max_rerank_ratio`
  (0.8) × gold и почти дословные дубли (Jaccard ≥ 0.6). Цена — not_found-примеры без
  ловушек «почти ответ», зато метки чистые.
- Фильтр: с gold — не not_found, verify пройден, процитирован именно gold, ответ
  ≤ 700 симв.; без gold — учитель сказал not_found (иначе в контексте нашёлся ответ);
  дубли вопросов к одному пункту (Jaccard ≥ 0.8).
- `Teacher`: OpenAI-совместимый клиент, кэш на диск по хэшу запроса (`data/synthetic/
  cache/`) — повтор бесплатный, обрыв продолжается с места; ретраи с backoff; откат с
  `json_schema` на `json_object`, если провайдер не умеет схему; `workers` потоков.
- Пилот (учитель = локальная Qwen3-4B, 20 пунктов — только проверка конвейера): 56 вопросов
  (число 11, можно ли 15, условие 11, разговорный 19), совпадение слов вопроса с пунктом —
  медиана 0.38; оставлено 38/56 (68%), not_found среди оставленных 32%. Отсев: verify 7,
  «нашёл ответ без gold» 6 (учитель-4B натягивает ответ по постороннему пункту), gold не
  процитирован 5, отказ при gold 2, длинный ответ 1. Кэш: повтор — 64 из 76 из кэша.
- Наблюдения к прогону с большим учителем: размытые разговорные вопросы («как учитывать,
  когда ставят извещатели») отвечаются многими пунктами; часть вопросов списана с пункта
  почти дословно — после прогона решить, нужен ли фильтр по `lexical_overlap`.
- Попутно: `LLM_BASE_URL` теперь `127.0.0.1`, не `localhost` — localhost резолвится в
  IPv6 ::1, где 8080 слушают Docker Desktop и WSL; запросы уходили им и получали 404.
- **Нужно от владельца**: `.env` с `TEACHER_BASE_URL`, `TEACHER_API_KEY`, `TEACHER_MODEL`
  (open-weight, например Qwen3-235B-A22B-Instruct-2507 — лицензия позволяет обучать на
  выходах). Оценка полного прогона (2000 пунктов): ~2 тыс. запросов на вопросы + ~5,5 тыс.
  на ответы, ~15 млн входных токенов; этап контекстов ~45 мин на GPU.
